Problem / thesis

Design tokens are usually reconstructed by hand

Zooming into screenshots, guessing hex values, eyeballing padding — then re-entering the same decisions into every toolchain. Copy That’s contract: screenshot → reliable design tokens → W3C + CSS (and React / Tailwind) export, with a light overview narrative. Lighting, geometry, and mood board stay parked until the spine earns the right to grow.

Hard parts

Where judgment meets systems

CV + Claude extractors

Computer vision maps structure; the model names and organizes the way a designer would. Families live under src/copy_that/extractors/ with an explicit capability map — not a single opaque prompt.

Compat+ vs strict DTCG

Export-complete coverage of official $types with intentional deltas (hex colors, spacing section naming, layout group). Documented in W3C_CONFORMANCE — no silent “close enough.”

Park vs delete

Mood board, lighting, geometry, sessions stay mounted or in-tree but off default UI via feature flags. Spine first; platform later.

Design decisions

Selected highlights

  • W3C Design Tokens as interchange New families plug into the same graph → export path instead of bespoke formats per consumer.
  • Finish the spine before the platform P0–P3 center extract/export/overview; P4 parked intelligence; P5 platform only after the happy path is trustworthy.
  • Honest synth vs extract Some $types are derived or preset at export with confidence thresholds — documented rather than oversold as pure vision.
  • Illustrative ≠ shipped UI generation Fieldwork apps on the Home page show why tokens matter; the product ships extract + export, not auto-built applications.

What’s next

Deliberate promotion of parked work

Lighting, geometry, and mood board each need product criteria and a cost model before joining the default path. No calendar promises on this page — see the roadmap for phase intent.
